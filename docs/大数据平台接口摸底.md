## 1. 媒体查询 `/queryPage`

**用途**：输入日期（默认 2023-05）+ 一级/二级/三级标签（公交/地铁出入口/户外/上海地铁/观光车），查单个媒体的地图位置、覆盖、区域人流与画像。

**请求链路**：

```http
POST /label/queryFirstLabel
POST /label/querySecondLabel        firstLabel=公交
POST /label/queryThirdLabel         firstLabel=公交&secondLabel=A++
POST /label/queryLabelData          labelId=6687&dataMonth=202305&operType=
POST /bbf8e41e454b47126290905525c69f7
```

指标请求体（表单）：

```text
queryType=1
indicatorType=visitorsFlowrateAndcrowdSpeed
dataMonth=202305
labelIds=6687,6684,6540,474,406
gridIds=
extOptions={"gridType":"500","underground":"0"}
```

`indicatorType` 可用：`visitorsFlowrateAndcrowdSpeed`、`crowdAge`、`crowdGender`、`crowdConsumption`、`crowdHouse`、`crowdPhoneNew`、`regionAttribute`、`circleCross`。

**返回样例（`visitorsFlowrateAndcrowdSpeed`）**：

```json
[
  {"type":"coverPeoplesPV","time1":148018},
  {"type":"coverPeoplesUV","time1":134668},
  {"type":"coverPeoplesPVAccurate","time1":187405},
  {"type":"visitorsFlowrate","time1":57,"time2":86,"time3":67,"time4":46},
  {"type":"00:00 - 23:59","time1":0}
]
```

- `coverPeoplesPV` = 区域覆盖人群-日均人次；`coverPeoplesUV` = 日均人数；`coverPeoplesPVAccurate` = 触达日均人次。
- `visitorsFlowrate` 四段对应 7:00–10:00 / 10:00–16:00 / 16:00–20:00 / 20:00–22:00（来自 `visitorsFlowrateAndcrowdSpeed.js` 注释），**单位在页面未标，且地铁/公交量级不一致，只作相对比较**。

**能否批量**：可以，一次 `labelIds` 传多个（逗号分隔），返回合并后的 PV/UV/触达和一套画像。实测 5 个标签（3 公交 + 2 地铁口）正常返回。

## 2. 组合查询 `/comparePage`

**用途**：页面是媒体查询的“多选 + 比较”版；三级标签下拉 `multiple=true`，勾选“添加比较”（默认勾选），选择多条媒体后一次查询，右侧信息面板按所选媒体合并计算。

**实测操作**：

1. 一级标签选“公交”，三级标签多选 `66路`、`63路`、`17路`。
2. 再切一级标签“地铁出入口”，多选 `陆家嘴 2号口`、`3号口`。
3. 点“查询”。

**实际请求**（信息面板发出）：

```http
POST /bbf8e41e454b47126290905525c69f7
queryType=1&indicatorType=visitorsFlowrateAndcrowdSpeed&dataMonth=202305
labelIds=6687,6684,6540,474,406
gridIds=&extOptions={"gridType":"500","underground":"0"}
```

**结果对比**：

| 选择 | 区域 PV | 区域 UV | 触达（PVAccurate） |
|---|---:|---:|---:|
| 仅 3 条公交（66/63/17） | 331.50 万 | 183.14 万 | **36.94 万** |
| 加 2 个地铁口（陆家嘴 2/3 号口） | 346.30 万 | 196.60 万 | **56.41 万** |

结论：**组合查询能算“多线路 + 多地铁口”的合计触达，但“去重”只发生在同一个 500m 网格内；跨网格是相加，不是自然人级去重。**

补充实测（同一指标接口，2026-11-21 17:00）：

| 组合 | 分查相加（触达） | 合并查（触达） | 说明 |
|---|---:|---:|---|
| 陆家嘴站 5 个口（同网格 C22389） | 603,719 | **120,744** | 同网格去重 |
| 人民广场 10号口 + 11号口（不同网格） | 45,119 | **45,119** | 跨网格相加 |
| 2 条公交 + 2 个地铁口（跨媒体） | 85,037 | **85,037** | 跨媒体相加 |

PV 同理：同网格 5 口 740,090 → **148,018**；跨网格 73,775 → **73,774**；跨媒体 425,234 → **425,233**。

上面“3 公交 + 2 口 = 56.41 万”之所以低于直接相加，是因为那 2 个口（474/406）在**同一个网格**，触达做了并集；如果换成两个不同网格的地铁口，合计就会接近相加。

因此对外口径应写“区域触达合计（500m 网格并集，跨区可能重复）”，不能宣称“自然人级去重”。

**注意**：

- `compareDiv` 的“对比线路”预设列表为空：`POST /label/queryThirdLabel {baseCompare:1}` 返回 0 条，平台没有预置对比线路；多选靠三级标签下拉自己选。
- “已选择媒体”列表在 `#chooseDiv`，页面截图时该区域未渲染出文字（但信息面板已按所选 `labelIds` 计算）。

**能否批量**：可以，一次请求带全部 `labelIds`；UI 支持多选。

## 3. 自由查询 `/looseQuery`

**用途**：在地图上画圆/多边形/矩形，按边界反查区域内的媒体和网格。

**请求**：

```http
POST /label/queryLabelByBorder
border=121.470 31.228,121.480 31.228,121.480 31.238,121.470 31.238,121.470 31.228
dataMonth=202305
isHD=0
```

- `border` 是“经度 纬度,经度 纬度…”（高德/GCJ-02），首尾闭合。
- `isHD` 是否高清（0/1）。

**实测（人民广场附近约 1km 方块）**：

- `labels`：**47 条**，含户外 LED（来福士广场 LED）、人民广场地铁口、上海地铁线路等。
- `grids`：**1 个**，字段 `{id:"C1082", center, border, crowdDensity:"87245.89005"}`。
- 返回还有 `numStr`、`sopExtendData`。

**能否批量**：一次返回区域内全部媒体；页面可一键把 `labels` 全部加入信息面板算合并人流。

**价值**：可做“任意圈选区域 → 媒体清单”，比固定锚点灵活；`crowdDensity` 是网格级人流密度，可做热力图。

## 4. 条件查询 `/conditionQuery`

**用途**：按行政区、街道镇、商圈、地理属性、POI、月日均人次/人数、年龄、性别、房产、消费（含收入档）筛选，反查符合人群条件的媒体与网格。

**接口**：

```http
POST /conditionQuery/queryAllCondition
```

返回 **342 条**条件定义，字段：`id / firstType / secondType / thirdType / conditionName / conditionId / minValue / maxValue / dataItem`。

```http
POST /label/queryLabelByQueryCondition
queryCondition=<id 列表>
dataMonth=202305
```

`queryCondition` 拼接规则（来自 `conditionQuery.js`）：

- 同一个下拉多选内的值用 `;` 连接；
- 不同下拉之间用 `,` 连接；
- 例：`19,113` = 商圈“陆家嘴商圈”(id 19) + 消费高/1 万以下(id 113)。

**实测组合**：

| queryCondition | 含义 | labels | grids |
|---|---|---:|---:|
| `19` | 陆家嘴商圈 | 95 | 175 |
| `19,113` | 陆家嘴商圈 + 消费高（1 万以下） | **77** | **171** |
| `19,114` | 陆家嘴商圈 + 消费高（1–5 万） | 47 | 4 |
| `19,117` | 陆家嘴商圈 + 消费较高（1 万以下） | 57 | 135 |
| `19,61` | 陆家嘴商圈 + 30–40 岁（1 万以下） | 63 | 158 |
| `19,64` | 陆家嘴商圈 + 30–40 岁（10 万以上） | 0 | 95 |
| `19,64,116` | 商圈 + 30–40 岁 10 万以上 + 消费高 10 万以上 | 0 | 0 |
| `64` | 30–40 岁 10 万以上（不限商圈） | 292 | 12 |
| `116` | 消费高 10 万以上（不限商圈） | 0 | 0 |

**结论**：

- **“按人群反查媒体”在条件查询里，成立**：能直接返回媒体 `labels` 和网格 `grids`。
- 但**人群条件数据很稀**：消费高 + 10 万以上 = 0 条；商圈 + 30–40 岁 + 10 万以上 = 0 条媒体（只有网格）。做演示要选“1 万以下 / 1–5 万”这类实际有数据的档位，不能默认选最高收入档。
- 条件的 `id` 是行的唯一 id（不是 `conditionId`）；页面下拉的 option value 就是 `id`。

**能否批量**：可以，多条件一次请求；返回媒体清单+网格。

## 5. 定制查询 `/looseMultiQuery`

**用途**：一次输入多个地点（分号/中文分号/换行分隔）+ 查询范围（100–2500m），逐个地点解析、画圈，再合并媒体；页面对 `labels/grids` 按 id 去重。不是人群反查。

**实际流程**：

1. `queryAddress` 输入多个地址；
2. `mapOperButton`（地点解析并绘制）→ 用 **百度 JS `BMap.Geocoder`** 逐个解析（每 400ms 一个）；
3. 每个点按 `queryRange` 画圆/多边形；
4. 点“查询”→ 对每个区域调 `POST /label/queryLabelByBorder`，带 `numStr=1,2,...`；
5. 前端 `uniqueFun(labels,"id")` / `uniqueFun(grids,"id")` 去重。

**实测**：

- UI 自动解析失败（提示“未获取到边界信息，请确认！”），原因是该页依赖百度地图 JS Geocoder，IAB 环境里未能完成绘制；这是页面实现问题，不是接口问题。
- 用页面同款接口直接发两个区域的边界（人民广场方块 + 徐家汇方块）：
  - 区域 1：47 条 labels；
  - 区域 2：30 条 labels；
  - 合计 77，按 id 去重后 **76**（1 条线路跨两个区域，被去重）。
- 页面还提供 POI 属性多选、红豆线路、坐标汇总、导出。

**能否批量**：可以，多地点批处理 + 去重；一次一个区域一个 `queryLabelByBorder` 请求，前端负责合并。

**结论**：定制查询 = 多地点/多半径合并，不是按人群反查。按人群反查请用条件查询。

## 6. 媒体覆盖分析 `/nearbyPoiLineQuery`

**用途**：地点 + 半径 + 媒体类型，返回覆盖到的公交线路/地铁线路（我们现有覆盖数据的来源）。

**请求**：

```http
POST /nearby/geocode
{"address":"徐家汇","city":"上海市"}

POST /baseInfoLine/matchCoverLines
{"radius":3000,"mediaTypes":["bus","metro"],"lineScope":"self",
 "centers":[{"name":"徐家汇","address":"徐家汇","lng":121.45237276040281,"lat":31.19777439300676}]}
```

**实测（徐家汇 3km）**：

- geocode「徐家汇」：`level=乡镇`、`confidence=25`，落在街道办，偏东约 1.4km。
- 已改用「徐家汇商圈」（`level=生活服务`、`confidence=70`，121.4379 / 31.1984）重跑：1km **22 条**（16 公交 / 6 地铁）、3km **41 条**（30 公交 / 11 地铁）。
- 返回字段：`lineName / mediaType / minDistance / nearestStaName / nearestStaLng / nearestStaLat / linePath / centerName / centerLng / centerLat / radius`。

**能否批量**：`centers` 是数组，理论上可传多个中心；当前 UI 一次一个中心。批量合并需要自己按中心去重。

## 7. AI线路 `/busLineShowSolution`

**用途**：不是“AI 推荐线路”，而是线路预览/方案编排工具：左侧公司/级别树选线路，地图预览几何，填备注保存方案、看历史记录。

**接口**：

```http
GET /baseInfoLine/getTreeLine
```

返回 12 个根（新云-最新1225、新云-都市观光、新高度、水陆通、DG-0520、TD-0521、BY、ST、GF、CZ、QT公司、地铁线路），共 **1643 个节点、1628 条线路节点**；节点字段：`lineId / lineName / linePath / staName / staLocaltion / name / children`。

```http
GET /baseInfoLine/getLineJson?linePath=D:\SOP\media-res\JSON\66路
```

返回：

```json
{"code":0,"data":"[{\"name\":\"66路(龙华东路制造局路-丰镇新村)\",\"path\":[{\"lat\":121.4961,\"lng\":31.2014}, ...]}]"}
```

**坑**：`path` 里的 `lat` 字段实际存的是经度、`lng` 存的是纬度（字段名反了），直接按字段名用会画错。页面自己的 `showData` 也按反的读。

**能否批量**：树可多选；几何接口一次一条线，批量需要循环调用。

**结论**：对 P0 提案工作台没有直接增量价值（我们已经有覆盖 CSV + 自抓几何），可用来补线路几何或做方案保存/历史。

## 8. AI线路-站点 `/busLineShowSolutionStation`

**用途**：预期是 AI线路的“站点级”版本；实际页面与 AI线路几乎一致，只是 `readFile` 多了 `staLocaltion/staName` 参数：有站点坐标就只画点，没有就画整条线。

**能否批量**：无站点数据，批量为空谈。

## 9. 对我们工作台的结论

1. **组合查询的回答：能算合计，但只在同 500m 网格内去重。** 多个 `labelIds`（公交+地铁口）一次请求，`coverPeoplesPVAccurate` 是“网格并集”后的合计；同站同网格会去重（5 口 60.37 万→12.07 万），跨网格/跨媒体基本相加（2 公交+2 口 8.50 万→8.50 万）。不能宣称自然人级去重。
2. **定制查询的回答：不能按人群反查。** 它是多地点+半径的合并查询；按人群反查在**条件查询**。
3. **条件查询可用但要避坑**：选“消费高/较高 + 1 万以下/1–5 万”有数据（77/47 条），选“10 万以上”经常 0 条；演示时不要默认最高档。
4. **覆盖分析仍是锚点覆盖的主入口**：`geocode` 的乡镇级落点会偏；陆家嘴已改成陆家嘴金融城，徐家汇已改成徐家汇商圈。其他锚点坐标也要人工核对。
5. **自由查询/定制查询能补“任意圈选/多地点”**：如果评委临时报一个地址，可以用 `queryLabelByBorder` 现场反查媒体；比固定 7 锚点灵活。
6. **AI线路/站点对 P0 无增量**：没有站点级人流，几何也与已有数据重复。

## 10. 复现提示

- 所有 38880 请求必须在已登录的 IAB 里发；Python/curl 直连被网络/代理挡住。
- 登录态是 `jsessionid`（HttpOnly）+ 图形验证码；会话会过期，过期后重新登录（不绕验证码）。
- 指标接口是同一个：`POST /bbf8e41e454b47126290905525c69f7`，靠 `indicatorType` 区分人流/画像/POI/商圈。
- `queryLabelByBorder` 的 `border` 用高德坐标；页面内部会把百度坐标 `baiduToGaoDe` 后再发。
- `getLineJson` 用 GET；POST 会 405。`getTreeLine` 也是 GET。

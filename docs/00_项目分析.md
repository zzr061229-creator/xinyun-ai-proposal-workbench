## 0. 结论先行

**一句话定位**

不要做成"AI 写 PPT"，要做成**"把红豆库存变成一份可下单的投放方案"**：给定行业、预算、媒体、档期，90 秒内输出带库存证据、价格口径、排期和替补的 HTML 提案；预算从 100 万拖到 500 万时，方案结构随之升级，而不是数量乘 2.5。

**三个必须赢的判断**

1. **真库存是生死线。** 每一条线路/点位必须能回到红豆的查询日期、空车数、合同/预定占用。评委随机点一条问"这条现在还有车吗"，答不上来就全盘失信。
2. **会算账比会写字值钱。** 刊例→折扣→净价→制作/监测，直客/4A 双口径。这是销售每天真正花时间的地方，也是通用 AI 最容易编造的地方。
3. **现场应变决定名次。** 评委现场指定行业/预算/媒体，系统必须 2 秒重排、10 秒出稿；预录、截图、固定 5 套模板都会露馅。

**推荐打法**

- 主打演示：**私立医院（和睦家/嘉会类）+ 200 万 + 地铁+公交 + 2027 Q2**。地理精准度最高，最能证明"需求与媒介结合"。
- 现场变招：**乐园 + 500 万 + 暑期**，证明档期策略与规模伸缩；再让评委砍到 100 万 / 只投地铁，证明复用性。
- 交付形态：**静态优先的 Web 工作台 + 单文件 HTML 提案**；断网也能演示，数据快照带时间戳。

**最大风险**

资料包/账号尚未到手，价格与合同口径未知。若按想象写折扣，现场会被企业评委一句问穿。

## 1. 赛题到底在考什么

### 1.1 表面需求 vs 真实痛点

| 表面 | 真实 |
|---|---|
| 当天出一份提案 | 销售要在"库存不确定 + 价格可谈 + 客户需求模糊"三件事同时存在时，快速给出一个**敢承诺、能执行、有利润**的组合 |
| 方案要好看 | 方案要**可核对**：哪条线、几辆车、哪天有、什么价、为什么选它 |
| 支持 100–500 万 | 不是三套模板，而是**一套库存图上的三种结构**：单点打透 / 双线协同 / 全城战役 |
| AI 生成 | AI 只该做它擅长的：洞察叙事、理由生成、文案与合规初筛；**选点和算价必须确定性** |

### 1.2 输入输出

- 输入四项：行业（5 选 1）、预算（100/200/500 万）、媒体（公交/地铁/组合）、档期（2027 年内，以红豆可售为准）。
- 隐含第五项：**品牌**——行业内自选一家在上海有线下门店的头部企业。
- 输出：HTML 提案（品牌理解、媒介组合、线路/点位清单、排期、报价），可交互、可演示、可复用。

### 1.3 评分反推（按赛题文本，非官方评分表）

| 维度 | 权重假设 | 评委实际会看什么 | 我们的对策 |
|---|---:|---|---|
| 需求与媒介结合 | 30% | 品牌/人群→门店/地标→覆盖→线路→组合，链路是否自洽、有证据 | 地图锚点 + 2023 人流 + 每条线路的理由标签 |
| 可运行/现场应变 | 25% | 换行业/换预算/换媒体，能否当场出结果；是否真数据 | 静态引擎 + 预算滑块 + 快照时间戳 |
| 复用性 | 15% | 新客户是否 10 分钟出案；改预算是否 2 秒重排 | 配置驱动 + 结构随预算变化 |
| 专业度/完成度 | 20% | 报价口径、排期、合同条款、监测、导出 | 刊例/折扣/净价、误一补二、替补池、CSV/Excel |
| 创新 | 10% | 有没有公司没想到的解法 | 可下单提案、销售/客户双视图、合规闸门 |

### 1.4 隐藏考点

1. **库存按日期**：不是查"今天空车数"，而是查档期内每一周的可售；合同车/预定车要区分。
2. **价格口径**：刊例是区间化口径，折扣有阶梯；4A 与直客不是一套算法。
3. **2023 人流**：平台数据月份是 2023，只能做相对比较，不能包装成 2027 绝对值——诚实标注反而加分。
4. **提案承诺**：资料包 03 的"误一补二""监测条款"是提案里可以承诺的依据；乱承诺会变成交付风险。
5. **复用**：评委可能要求"同一个客户，预算从 200 万加到 500 万"，看的是结构升级，不是数量堆叠。

## 2. 产品定义

### 2.1 定位

**新云提案引擎 / Media Flight Deck**：把库存台账变成可下单的投放方案。

- 对销售：4 个旋钮（行业/品牌、预算、媒体、档期）→ 90 秒出案；改预算 2 秒重排。
- 对客户：一份可演示、可追溯、可执行的 HTML 提案。
- 对公司：把"翻刊例、查空位、算折扣"的经验，沉淀成可复用的规则。

### 2.2 核心链路（必须可视化）

1. **品牌/行业**：行业模板 → 品牌档案（定位、人群、门店/院区/园区、campaign 目标、合规约束）。
2. **需求锚点**：把门店/地标变成地图上的点，给权重（旗舰店/社区店/院区/乐园入口）。
3. **覆盖分析**：锚点 + 半径 → 大数据平台周边媒体 + 2023 人流 → 候选池。
4. **库存校验**：候选池 ∩ 红豆可售（按周查空车数）→ 可投池；合同/预定单独标记。
5. **组合优化**：预算 + 媒体配比 + 区域多样性 + 档期连续性 → 选线/选点。
6. **排期/报价**：波次、上下刊、换画；刊例→折扣→净价→制作/监测。
7. **提案输出**：客户版 + 销售版 + CSV/Excel + 单文件 HTML。

每一步在界面上都要有状态、耗时、数据来源；这是"可信"的一部分。

### 2.3 六个模块

| 模块 | 作用 | 关键设计 |
|---|---|---|
| Brief 解析 | 行业/品牌→结构化需求 | 5 套行业模板 + 品牌预设 + 任意品牌兜底 |
| 地理锚点 | 门店/地标→地图点+半径 | 支持手动加点和公开信息核验 |
| 覆盖分析 | 锚点→周边媒体+人流 | 调用/复刻大数据平台；标注 2023 口径 |
| 库存校验 | 候选→可售 | 按周空车数、查询日期、合同/预定、替补池 |
| 方案优化 | 预算内选组合 | 确定性贪心+局部交换；可解释 |
| 提案渲染 | 输出 HTML/表格 | 双视图、预算滑块、导出 |

### 2.4 双视图 + 预算滑块

- **客户视图**：品牌洞察、策略、地图、清单、排期、报价、监测承诺；隐藏折扣底线与内部备注。
- **销售视图**：每条线路的空车数、合同/预定、折扣底线、毛利估算、锁定截止、替补建议、客户异议提示。
- **预算滑块**：100–500 万连续拖动；不是删条目，而是重排结构（媒体配比、波次、区域覆盖），并显示 diff："+12 辆车 / +1 个地铁口 / 覆盖 +2 个商圈 / 净价 +98 万"。

这个双视图是"办公工具"与"演示 PPT"的分水岭：评委看到的是销售明天真的会用的东西。

### 2.5 复用性

- 新客户：选行业模板 → 填品牌/锚点 → 选预算/档期 → 生成；目标 <10 分钟。
- 同客户改预算：<2 秒重排 + 10 秒重渲染。
- 同客户换媒体：勾选即重算，保留锚点与档期。
- 版本：客户版/销售版/执行版同源；导出 HTML/CSV/Excel。
- 度量：界面上显示"人工 3 天 → 本单 90 秒；改预算 0.5 天 → 2 秒"。

### 2.6 办公工作流（AI+办公赛道的加分项）

- 角色：销售 / 提案 / 主管 / 客户。
- 状态：草稿 → 内部评审 → 客户版 → 锁定 → 执行。
- 审批：折扣低于底线或超预算时，触发主管审批（P1/P2）。
- 版本对比：v1/v2 的线路、预算、折扣 diff。
- 交接：提案 → 排期订单 → 执行清单，一份数据贯穿。

48 小时内不必全做，但演示时提一句"这套数据模型天然支持审批与交接"，能体现办公场景理解。

| 行业 | 目标客户候选（需核验门店/网点） | 需求锚点 | 媒介重心 | 黄金档期 | 创意/合规要点 |

| 乐园 | 上海迪士尼、海昌海洋公园、欢乐谷、乐高乐园 | 园区、交通枢纽、家庭社区 | 地铁直达线 + 旅游/跨区公交 | 暑期 7–8 月；国庆；春节 | 家庭亲子/节日活动；安全提示 |

**推荐主打：私立医院。** 理由：地理精准度最高（院区 3km + 地铁出口方向），最能展示"覆盖分析→选点"的链路；医疗合规又能拉开与通用方案的距离。**第二现场变招：乐园**，展示档期与规模。

> 说明：以上品牌为候选，门店/院区数量与位置需按公开信息核验；不在提案里编造具体门店数。

### 3.1 媒介角色分工

- **地铁出入口 = 到达/导流**：人流高、离消费/就诊/入园动作近、品牌背书强；点位贵，适合"临门一脚"。
- **公交车身 = 覆盖/频次**：线路走廊广、重复曝光、CPM 低；适合"全城看见"。
- **组合逻辑**：地铁打"精准到达"，公交打"广度频次"；比例按行业调整（医院偏地铁，快消偏公交，银行/乐园居中）。

## 4. 数据与系统

### 4.1 红豆（flairmedia.com.cn:881）

- 媒体管理 → 媒体库：公交 552 条、地铁 861 条；空车数=可售，合同车/预定车=占用；点数字看明细。
- 库存**按日期**查询；提案排期必须逐周核对。
- 可导出；导出是数据底座，界面截图是证据。
- 待确认字段：线路名/方向、车辆总数、空车数、价格、媒体形式、区域、上刊周期、制作费。

### 4.2 大数据平台（flairmedia.com.cn:38880）

- 区域人流：数据月份选 **2023**；用于相对权重，不包装绝对值。
- 媒体覆盖分析：地标/坐标 + 半径 → 周边公交/地铁媒体；这是"锚点→候选"的官方链路。
- AI 线路：画线、保存、生成 HTML 预览链接；可作为"线路故事"的佐证，但外链可能需登录，演示以本地地图为主。

### 4.3 资料包优先级

1. **07 媒体刊例价**：报价底座（区间化口径）。
2. **03 合同三份**：直客/4A/排期订单；误一补二、监测条款、付款。
3. **08 系统使用说明**：账号、查询、导出。
4. **01 公交台账**：字段说明与静态参考（注意 431 条 vs 红豆 552 条的差异，以红豆为准）。
5. **05 历史提案 / 06 客户 brief**：提案结构与输入样本。
6. **02 上下刊流程 / 04 结案监测**：执行与承诺依据。
7. **00 企业介绍**：公司话术与资源规模。

### 4.4 数据坑清单

| 坑 | 影响 | 对策 |
|---|---|---|
| 库存按日期，不是实时总数 | 推荐了已售线路 | 逐周查询；空车数≥需求；显示查询日期 |
| 合同车/预定车混淆 | 把预定当可售 | 三态分开；预定车需确认释放 |
| 431 vs 552 条线路 | 数据对不上 | 以红豆导出为准；资料包仅参考 |
| 2023 人流 | 被质疑数据旧 | 明确"相对权重"，不承诺绝对值 |
| 刊例区间化 | 报价不可直接对外 | 用折扣阶梯与净价；标注口径 |
| 4A/直客差异 | 报价算错 | 双口径引擎；按合同配置代理费/返点 |
| 地铁点位方向 | 选错出口 | 点位带出口/方位；锚点距离+方向双校验 |
| 制作/监测费漏算 | 预算超支 | 报价含制作、监测、税费；预算校验 |

## 5. 技术方案

### 5.1 架构：静态优先

```
资料包/系统导出 → Python 清洗 → inventory.json + anchors.json + rules.json
                                      ↓
                        前端（React/Vite 或原生）内嵌数据
                                      ↓
                     浏览器内规划引擎（JS）→ HTML 提案
```

- **为什么静态优先**：现场网络不可控；评委要"当场出结果"；单文件 HTML 可直接发客户。
- **数据量**：1413 条媒体记录 + 价格/坐标，JSON 约 1–3 MB，内嵌无压力。
- **刷新**：比赛当天早上从红豆导出一次，重建 JSON；界面显示"库存快照：2026-11-21 10:30"。
- **可选服务端**：FastAPI/Node 仅用于刷新与 LLM 调用；演示不依赖。

### 5.2 规划引擎（确定性）

- 输入：锚点集合 A（含权重）、媒体池 M（含价格、周可售）、预算 B、媒体配比约束、档期 W。
- 打分：`score(m) = Σ_a w_a × footfall_a × decay(dist) × format_fit + corridor_bonus - risk_penalty`
- 选择：按 `score/price` 贪心，满足预算/配比/区域多样性约束；再做局部交换（1-1、1-2）提升。
- 输出：条目清单 + 每条理由（贡献最大的锚点、覆盖人流、可售证据）。
- 可解释性：每个条目都能展开"为什么是它"。

### 5.3 报价引擎

- 单价 × 数量 × 周数 = 刊例小计；折扣阶梯（按总量）→ 净价；加制作费、监测费、税费。
- 直客/4A 两套口径；4A 的代理费/返点按 03 合同配置。
- 预算校验：合计 ≤ 预算；显示余额/超支；超支时给出"降档建议"（换点位/减周数/换媒体）。
- **不写死折扣数字**：全部参数化，等 07/培训口径确认后填入。

### 5.4 地图/可视化

- 上海区级 GeoJSON + 锚点/媒体点/线路；ECharts 或 Leaflet。
- 无坐标时的兜底：区级质心 + 线路起终点示意；明确标注"示意"。
- 视觉概念：**城市投放塔台**——深色地图、发光线路、等宽数据字；客户版切换为浅色编辑风。
- 三个关键视觉：预算分配环、覆盖热力/半径、排期甘特。

### 5.5 LLM 用法（边界清晰）

| 用 LLM | 不用 LLM |
|---|---|
| 品牌/行业洞察叙事 | 选线、选点 |
| 每条线路的"人话理由" | 价格计算、折扣 |
| 创意文案 + 合规初筛 | 库存可售判断 |
| 提案章节草稿 | 排期日期计算 |
| 评委异议 Q&A | 预算分配 |

- 事实注入：把 plan JSON 作为唯一事实源，LLM 只做表达；数字不得由模型生成。
- 离线策略：赛前预生成 5 行业叙事模板；运行时模板+数据填充；有 API 再开"实时生成"。

### 5.6 导出/部署

- 单文件 HTML（内嵌数据与样式）→ 客户可直接打开；工作台本身部署到本地/静态托管。
- CSV/Excel：媒体明细、排期、报价三张表。
- 分享链接：静态托管或本地局域网；现场备用 U 盘。
- README：运行说明、数据快照、口径、已知局限。

### 5.7 备选方案

- 若红豆无法批量导出：用浏览器自动化/人工导出 CSV；仍不可行则用资料包 01 台账 + 现场截图，明确标注"静态参考"。
- 若大数据平台无 API：赛前对 5 行业锚点各跑一次覆盖分析，保存 JSON/截图；现场只做本地计算。
- 若时间不足：砍掉 AI 线路、Q&A、PDF；保 P0。

## 6. 演示设计

### 6.1 4 分钟剧本

| 时间 | 动作 | 话术要点 |
|---|---|---|
| 0:00–0:30 | 痛点 | "客户当天要方案，销售翻刊例、查空位、算折扣要 3 天；单子被竞对拿走。" |
| 0:30–1:00 | 输入 | 请评委选：私立医院 + 200 万 + 地铁+公交 + 2027 Q2（或评委指定） |
| 1:00–2:00 | 生成过程 | 地图落锚点→3km 圈→覆盖分析→红豆空车数→组合；每步显示数据来源与耗时 |
| 2:00–3:00 | 提案 | 品牌洞察一句话、媒介角色、TOP 线路清单（每条有理由）、甘特、报价（刊例/折扣/净价） |
| 3:00–3:30 | 预算滑块 | 200→500 万：结构升级（加波次/加区域/加地铁配比），diff 可见；再砍到 100 万 |
| 3:30–4:00 | 销售视图 | 空车数/查询日期/折扣底线/替补池/锁定建议；导出 Excel/HTML；收尾"90 秒，可下单" |

### 6.2 三个 wow

1. **预算滑块不是乘法**：500 万方案的结构与 100 万不同（媒体配比、波次、区域），当场解释"为什么"。
2. **每条线路都有证据**：点开即见红豆查询日期、空车数、贡献锚点、覆盖人流；评委随机抽一条也不怕。
3. **双视图**：一键从"给客户看的提案"切到"给销售用的作战面板"，同一份数据两种语言。

### 6.3 评委 Q&A 预案

| 问题 | 回答 |
|---|---|
| 数据是真的吗？ | 红豆导出 + 查询日期 + 记录截图；快照时间在页面顶部 |

## 7. 差异化：公司没想到的 6 个点

1. **提案=订单草稿**：输出可直接转成排期订单（线路/车辆数/周次/价格/上下刊），不是 PPT。
2. **库存风险对冲**：替补池 + 锁定截止 + 误一补二的可执行化。
3. **双口径报价**：直客/4A 一键切换，代理费/返点/折扣底线透明。
4. **合规闸门**：金融/保健品/医疗文案的禁用词与必填提示，生成即拦截。
5. **档期智能**：不是让客户随便选日期，而是按行业旺季推荐窗口并解释。
6. **销售作战面板**：折扣底线、毛利、客户异议、替补建议——把"经验"变成"看得见"。

建议落地 1/2/6（与痛点最贴），3/4 作为加分演示，5 作为叙事亮点。

### 12.2 实际报价与触达基准（05 饮用水样本）

- 公交大三侧实际报价：**S 58,000 / A++ 48,000 / A+ 38,000 元/辆/月**；制作费 **5,000 元/辆**。
- 样本 150 辆：日触达 **14,756,000**，月触达 **442,680,000**；折合单车日均约 **9.84 万**、月均约 **295 万**，CPM 约 **15–16 元**。
- 样本套餐结构：100 条线路（主城区基本覆盖）/ 150 辆（主城区大范围）/ 200 辆（主城区+外环）；另有“赠送媒体”（LED、双层巴士）作为成交杠杆。
- 结论：**触达可以按“级别均值 + 线路实测”建模型**；05 的 48 条线路实测表就是现成的校准集。

### 12.3 公交台账（01）

### 12.5 执行卡点（02）

- 公交/地铁/大牌均需**夜间窗口施工**；单晚有作业上限，几十辆/数十个点位要**分批多日安装**，全部在约定发布日前完成；雨天停工。
- 前置链路：设计→定稿→内容审批→制作→夜间安装；监拍外包，完工后**隔天**才给照片。
- 提案排期必须包含 **T-14 制作/审批、分批安装、雨天缓冲**，不能承诺“今天签约明天上刊”。

### 12.6 系统操作要点（08）

- 红豆：媒体管理→媒体库；按线路名/级别/行车公司筛选；“空车数”=可售，“合同车/预定车”=占用；点数字看明细；**按日期查库存**；支持导出。
- 大数据：媒体查询的数据月份必须选 **2023 年**；媒体覆盖分析输入地标/坐标+半径（示例 100 米）反查公交/地铁；结果可导出 Excel；AI 线路可保存并生成 HTML 预览链接。
- 官方建议链路：品牌调研→圈门店/地标→覆盖分析→红豆核对→组合报价。

### 12.7 对前文的 8 条修正

1. **规模叙事**：按 07/05 刊例中值、92 折、含制作费实测：
   - 100 万 / 4 周：约 22 辆公交，或 1 个 A++ 地铁口 + 16 辆公交；
   - 200 万 / 6 周：约 3 个 A++ 地铁口 + 12 辆公交（或 2 口 + 18 辆）；
   - 500 万 / 6 周：约 6 个 A++ 地铁口 + 39 辆公交；500 万 / 12 周：约 3 口 + 21 辆。
   不要再写“200 万 45 辆 + 6 口”（实际约 572 万）或“500 万 90 辆 + 15 口”（实际约 2,490 万）。把“全城覆盖”改成“核心走廊 + 关键点位”。
2. **报价引擎**：按级别（S/A++/A+）+ 区间定价，不按单条线路定价；05 的 58/48/38k 可作默认中值，折扣参数化。
3. **触达模型**：公交用 05 的单车日均约 9.8 万、月均约 295 万作基准；地铁用平台人流/覆盖；全部标注“预估”。
4. **排期**：加入 T-14 制作审批、夜间分批安装、雨天缓冲；甘特图要有“制作/进场/安装/上刊/监测”节点。
5. **承诺**：4A 客户写“误一补二”，直客写“损一补一”；监测 SLA 按框架（T+1/T+5/月监测）写，不能混。
6. **导出**：4A 订单列就是模板——媒体/地区/位置/类型/尺寸/数量/起止/刊例/折扣/净价/制作/总价；工作台直接按这个格式导出“订单草稿”。
7. **数据真实性**：01 是静态样本，红豆才是实时；431 vs 552、2023 人流都要在页面标注。
8. **商务杠杆**：赠送媒体、折扣、账期是成交变量；销售视图要有，客户视图要藏。
